# DataAgent 升维设计｜从 NL2SQL 助手到自主数据分析 Agent

> **文档性质**：系统设计（介于设计方案与模块设计之间）｜**v0.1**｜2026-04-28
> **问题设定**：KDD Cup 2026 Data Agents（https://dataagent.top）的任务分类与基准形态
> **升级总纲**：**保留全部既有资产，在其上生长**——定位从「NL2SQL 多智能体数据分析助手」升维为「自主数据分析 Agent」；任务层与评测层升级，裁剪掉多模态重档。
> **配套文档**：`设计方案.md`（系统级）、`详细设计.md`（模块级）、`模型选型.md`

---

## 1. 为什么升维：三个理由

1. **公开基准即需求参照**：KDD Cup 2026 Data Agents 对 "Data Agent" 的定义（自主编排 Data+AI 生态完成复杂数据分析）与四大能力要求（任务分解规划 / 工具选择调用 / 异构数据推理 / 结果综合），恰好是"NL2SQL 助手"的完整进化形态——升级方向不是臆想，是国际顶赛验证过的需求结构。
2. **公开基准可外测**：DataAgent-Bench 基准数据与评测规则（列签名匹配 + Recall − λ·冗余惩罚）公开——项目可在公开基准上取得可复算的自测数字，评测结论可外部验证。
3. **与既有资产零冲突**：Olist 主场景、黄金集 72 条、Linking/few-shot/口径层、评测迭代框架全部保留；新增部分（编排层 / Python 工具 / 文档源 / 多步任务）都是"挂"在现有骨架上，不是推倒。

**定位口径（纪律，三条）**：

1. **自建项目**——参照公开基准的能力体系与评测方法，场景、数据、任务全部自建；
2. **实现独立**——代码、场景、任务集均为自建；
3. **可扩展性**——任务集与评测链路按基准接口设计，更换数据集即可复算。

| 资产 | 现状 | 升维后的角色 |
|---|---|---|
| Olist 主库（9 表 / 约 155 万行） | 主业务库 | **不变**——多步任务的数据底座 |
| 单步黄金集 72 条（五类分层） | 评测集 | **保留为一轨**——单步能力回归用 |
| Schema Linking（BGE + 同义词 + 外键桥接，抽检 11/11） | 检索层 | **保留**——内嵌于取数技能 |
| few-shot 库 23 条 + 防泄漏校验 | 检索层 | **保留**——同上 |
| 口径层 `config/metrics.yaml`（3 组歧义设计） | 配置资产 | **升级**——渲染为"指标口径文档"入库，成为文档检索源 |
| LangGraph 状态图（understand→link→gen→exec→interpret→respond） | 编排 | **整体包装为 `query_data` 技能**——成为编排层的一个工具 |
| SQL 安全守卫（只读 / 白名单 / 强制 LIMIT） | 安全 | **保留**——技能内部 |
| 执行反馈重试回路（≤2 次）+ 澄清回路（≤1 轮） | 回路 | **保留**——技能内部 |
| 评测 harness（run_eval + naive_baseline + validate_golden） | 评测 | **扩展**——支持多步任务与双轨评测 |
| trace 落盘（runs/） | 可观测 | **扩展**——从节点级 trace 到 DAG 级 trace |
| BIRD / CSpider / Archer 等 7 套评测素材 | 外测素材 | **保留**——跨库泛化外测继续 |

**结论：升级新增的只有四块——编排层、Python 计算工具、口径文档源、多步任务集与双轨评测。**

## 3. 升级架构：两级 Pipeline（技能内聚）

### 3.1 总体结构

```
┌──────────────────── 外层：任务编排层（新增） ────────────────────┐
│  起点 plan（任务分解 → 步骤 DAG）                                │
│    ↓                                                            │
│  展开 execute_step（按依赖并行/串行；失败就近重试；异常追加下钻）  │
│    ↓                                                           │
│  收束 respond（正常 / 降级 / 拒答 三路汇入，唯一出口）             │
└─────────────────────────────────────────────────────────────────┘
                              ↓ 每步调用一个"分析技能"
┌──────────────────── 内层：技能层（现有资产包装） ────────────────┐
│  query_data  ← 现有 NL2SQL Pipeline 整体（understand→…→interpret）│
│  compute     ← 新增：Python 计算（沙箱）                         │
│  search_doc  ← 新增：口径文档检索（Embedding）                    │
└─────────────────────────────────────────────────────────────────┘
```

**设计原则：延续"Pipeline 为核心"**——外层同样遵守 起点 → 展开 → 收束：单入口 `plan`、展开为步骤循环（就近回退）、唯一出口 `respond`。**技能内聚**——每个技能内部是自己的完整链路（query_data 内部仍走 understand→link→gen→exec→interpret），编排层只认"输入 → 结构化输出"，不关心中间过程。

### 3.2 外层编排层设计（新增）

**状态字段**（在现有 state 基础上扩展）：

```
task / plan: [Step] / step_results: {step_id: obs} / observations / current_step
/ retries / degraded / answer / trace: DAG 执行记录
```

**Step 数据结构**：`{ id, skill: query_data|compute|search_doc, input, depends_on: [id], expect: 结果要点 }`

**Planner（规划角色）**：把高层分析问题分解为 2–6 步的 DAG——
- 顺序链（查库 → 计算 → 结论）；
- 分支并行（两个区域分别查询 → 对比计算，`depends_on` 为空即可并行）；
- 迭代下钻（进阶）：executor 发现空结果/异常 → 追加下钻步骤（受 `max_steps=8` 硬限）。

**Executor（执行角色）**：按依赖拓扑逐步调用技能；同层无依赖步骤并行（Semaphore 控制）；单步失败 → 带错误上下文重试 ≤1 次 → 仍败则标记降级继续（不中断全任务）或走拒答。

**Verifier（验证角色）**：中间结果校验——查询结果集为空/数量级异常/口径不一致时触发下钻或澄清。一期以规则校验为主（空结果、行数阈值、NaN），LLM 校验为可选增强。

**Synthesizer（综合角色）**：多步 observation → 结论 + 关键数字 + 口径说明；数字必须来自 observation，禁止编造（提示词约束 + 输出后校验）。

### 3.3 三个技能

| 技能 | 输入 | 输出 | 实现 |
|---|---|---|---|
| `query_data` | 自然语言取数问题 | 结果集 + 口径说明 | **现有 Pipeline 整体包装**（零改动内部） |
| `compute` | 计算任务描述 + 上游数据引用 | 计算结果 + 计算过程 | 新增：LLM 生成 Python → **沙箱执行**（见 §3.4） |
| `search_doc` | 口径/定义类问题 | 文档片段 + 归纳 | 新增：口径文档库检索（BGE/Qwen3-Embedding） |

### 3.4 Python 沙箱（新增工程点）

- 执行环境：`exec` 受限命名空间——禁用 import（除白名单 `math/statistics/collections/itertools`）、禁文件与网络、禁内省；
- 超时：单次执行 ≤10s（信号量/子进程级超时）；
- 数据传入：上游 observation 以只读结构注入（`data` 变量），不落盘；
- 失败处理：执行异常 → 错误信息回填 LLM 重生成（≤1 次）→ 仍败 → 该步降级；
- 与 SQL 守卫并列——**"两类代码执行、两套安全策略"** 本身就是可讲的工程点。

### 3.5 口径文档源（新增素材）

- 将 `config/metrics.yaml` 的口径定义**渲染为人类可读文档**：`docs/口径手册.md`（指标定义、口径变体、计算逻辑、适用表）+ `docs/数据字典.md`（表/字段中文释义）；
- 入库：与 few-shot 相同索引管线（Embedding + 向量库），文档切片按"一个指标一节"；
- 用途：`search_doc` 回答"XX 指标怎么定义/含不含退款"；多步任务中"先查口径再算数"成为标准链路——**这正是异构数据推理的最小可信版本（库 + 文档两源）**。

## 4. 任务层升级：多步分析任务集

### 4.1 任务类型（自建 20–40 条）

| 类型 | 结构 | 示例 |
|---|---|---|
| 两源链式 | 文档 → 口径 → 查库 → 计算 → 结论 | "客单价怎么定义？按此口径算 2018 年月均值" |
| 分支对比 | 两分支并行查询 → 对比计算 | "2017 与 2018 年圣保罗州 GMV 增长率" |
| 复合计算 | 查库 → Python 计算 → 排序/占比 | "运费占比最高的三个品类及占比" |
| 异常下钻 | 查询 → 发现异常 → 追加下钻查询 | "哪些品类差评率异常高？最高的品类差评主要抱怨什么" |
| 口径澄清（多步版） | 多步中含口径歧义点 | "净销售额是多少"（需先澄清退款口径） |

**建设流程（与单步黄金集同纪律）**：LLM 起草 → 人工逐条校验 → 标准步骤序列 + 标准答案执行生成；防泄漏（题目不得与 few-shot 重叠）。

### 4.2 单步黄金集处置

72 条单步黄金集**全部保留**——作为"单步能力"的回归集（验证升维不退化单步水平）；评测报告分两张表：单步表（原五类）+ 多步表（新五类）。

## 5. 评测层升级：双轨制

### 5.1 内测轨（自建多步黄金集）

| 指标 | 口径 |
|---|---|
| 最终答案正确率 | 数值容差比对（相对误差 ≤1% 或整数精确） |
| 步骤序列准确率 | 实际技能调用序列 vs 期望序列（含参数要点） |
| 任务完成率 | `max_steps` 内走到 respond 且未降级 |
| 过程指标 | 单任务调用次数 / 端到端时延 / 重试与下钻触发次数 |
| **编排增益** | 同多步任务集上：无规划基线（直接单轮问答）vs 有编排——失败率对比 |

### 5.2 外测轨（KDD DataSpace 官方公测包对标）

- **数据**：官方 DataSpace 公测参考包（HF 镜像获取，SHA256 校验；410 题输入 + 60 公测参考包）；本环境对 60 题全量执行（含视频模态题——视频不可解析，已分层披露）；
- **评测规则**：**官方评测器**（vendored）——列一对一对齐 + 类型感知值比对 + 重复行多重性 + 顺序敏感项按序；双链路（A 单发取数 / B 取数+解读），输出 `prediction.csv`；
- **报告口径**：`eval/report_kdd.md` —— 公开基准上的**自测数字**（标注：官方公测包、模型档位、本地自测环境）；
- **第二对标（可选）**：DAB 基准（Berkeley）取 SQLite/DuckDB 子集跑同一评测器，验证跨库泛化。

### 5.3 Judge 增量

多步评测中 Judge 除"解读类回答"外，新增两项低频调用：中间 observation 的合理性判断（辅助失败归因）、外测轨争议样例仲裁。调用量仍在分级以内（见模型选型适配）。

## 6. 裁剪纪律（明确不做的）

| 不做 | 理由 | 去向 |
|---|---|---|
| 视频/图表模态任务（KDD Hard/Extreme 档） | 多模态栈与主线无关，scope 失控 | 二期扩展（README 预留） |
| Docker 镜像打包格式 | 外部评测平台的提交要求；本项目本地可复现即可 | 不需要 |
| 128K 级上下文工程（Extreme 档） | 本项目场景不触发 | 不需要 |
| 跨 4 种 DBMS（DAB 全量） | 一期聚焦 SQLite 单库 + 文档 | 可选对标子集 |

**一期边界一句话：库（SQL）+ 文档（口径）两源、Easy/Medium 难度、2–6 步任务——把"多步编排 + 异构推理 + 双轨评测"做扎实。**

## 7. 多 Agent 叙事合并

两个复现项目共享"多 Agent 协作"升级方向，本项目落点为**角色分工**（同图谱、异提示词、异职责）：

| 角色 | 职责 | 模型 |
|---|---|---|
| Planner | 任务分解、DAG 计划 | 生成模型（**建议开思考模式**——规划受益于慢思考） |
| Executor | 工具调用循环、失败重试 | 生成模型（**关思考**——执行要干净输出） |
| Verifier | 中间结果规则校验 | 规则为主（一期不耗模型） |
| Synthesizer | 结果综合、成稿 | 生成模型（关思考） |

**多智能体界定**：角色分工由提示词与节点承载（LangGraph 多角色节点的通行实践）；模型层面，Planner / Executor / Verifier / Synthesizer 复用同一生成模型的不同模式，Critic / Judge 为独立异构档。

## 9. 验收增量（在设计方案 §7 基础上新增）

1. 多步任务集 ≥20 条，最终答案正确率与步骤序列准确率**有实测数字**；
2. 编排增益可证：同任务集上无规划基线 vs 有编排的失败率对比；
3. KDD 公测集外测数字进报告（含来源与口径标注）；
4. Python 沙箱安全策略（白名单 / 超时 / 禁网禁文件）落进代码且有失败样例；
5. 口径文档源入库并支撑 ≥1 条"先查口径再算数"的完整任务；
6. trace 升级为 DAG 级（步骤依赖 + 并行关系可回放）。
