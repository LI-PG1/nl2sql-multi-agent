## 1. 需求推导：链路对模型的约束

### 1.1 调用点清单（模型 → 链路映射）

| # | 调用点 | 角色 | 频率 |
|---|---|---|---|
| 1 | `gen_sql` SQL 生成 | 生成 | 每问 1 次 |
| 2 | 重试：错误反馈定向重生成 | 生成 | ≤2 次/问 |
| 3 | `interpret` 结果解读 | 生成 | 每问 1 次 |
| 4 | 澄清话术兜底（主路径为模板） | 生成 | 少量 |
| 5 | 评测打分：解读类回答 | Judge | 评测批量 |
| 6 | 两处检索：Schema Linking / few-shot | Embedding | 每问 2 次 |
| 7 | 意图 / 口径识别增强（默认规则实现） | 轻量档 | 二期 |
| 8 | 检索精排（当前设计无此环节） | 精排 | 备用 |

> **v0.2 升维后**（`DataAgent升维设计.md`）：调用点扩展为——Planner（任务分解，开思考）/ Executor（技能调用循环，关思考）/ Synthesizer（综合成稿，关思考）/ compute（Python 生成，Coder 对口）/ search_doc（口径文档检索）；生成角色由"SQL 生成"扩为"SQL + Python 双代码生成"。适配细节见 **附二**，选型表不变。

### 1.2 生成模型：六项要求

| # | 要求 | 说明 |
|---|---|---|
| 1 | SQL / 代码生成力 | 第一杠杆；SQL 属结构化代码，与代码模型的训练分布同构 |
| 2 | 中文语义 → SQL | 主题库为中文；需中英双语（BIRD 为英文、CSpider 为中文） |
| 3 | 输出可控性 | 单块 SQL、可解析、不夹思考过程、不拒答正常问题 |
| 4 | 跨库泛化 | BIRD / CSpider 为未见库，不能只对 Olist 过拟合 |
| 5 | 工程侧 | OpenAI 兼容、temperature=0、批量稳定（约 200–300 次调用/全量轮） |
| 6 | 上下文容量 | 单请求约 2–4K tokens；全候选满足，非区分项 |

### 1.3 Judge 与 Embedding

- **Judge 硬约束**：与生成模型不同厂牌、不同训练源——避免自评偏置（详细设计 §7.2）；判断力（问题 × SQL × 数据 × 解读一致性核对）；中文；量化 / 部署形态下的打分稳定性（配人工复核 30–50 条）。
- **Embedding**：中文为主、兼容英文 schema 名与英文题；高频低延迟（本地 / 内网服务优先）；保留可替换性。

## 2. 市场扫描（2026-10）

### 2.1 四个生态位的关键事实

**① 通用开源旗舰（2026 年中）**：国产开源全面领跑——DeepSeek V4-Pro（1.6T / 49B 激活，MIT，SWE-bench 80.6 / GPQA-D 90.1 / HLE 48.2）、Kimi K3（2026-08 开源，综合横评最强）、GLM-5.3、Qwen3.8 系（Max 2.4T / Flash-Next 125B-6B 激活）等。**含义：开源天花板已逼近闭源前沿，但 1T 级模型不适合本项目的部署形态**（本项目要可复现、低成本回归）。

**② Coder 专线快速迭代**：Qwen3-Coder-30B-A3B（2025-07，本项目 v0.1 基线）→ **Qwen3-Coder-Next**（2026-02，80B / 3B 激活，256K，专为编码智能体与本地开发设计，原生非思考模式输出）→ **Qwen3.6-Coder-32B**（2026 上半年，128K，Spider 2.0-Lite 88.7%，被第三方评测列为"本地 SQL 生成裁决之选"）。**含义：生成主选应换代**。

**③ Text-to-SQL 专用模型崛起（重要市场信号）**：一批执行反馈 RL 训练的专用模型（Arctic-Text2SQL-R1/R2、Databricks RLVR-32B、SiriusAI-32B v2、SQLWeaver-32B 等）在 BIRD 单模型轨达 **74–76%**，超过 GPT-5.5-xhigh（72.5）与 Claude Opus 4.6（70.1）；BIRD 单模型轨第一为 Gemini-SQL2 80.04%（Google，2026-06，**未发布独立可用形态**）。**含义：需单独评估专用路线（见 §3.4）**。

**④ 向量与裁判生态**：Embedding 侧 Qwen3-Embedding 系（8B 多语言 MTEB 榜首 70.58，0.6B / 4B / 8B，Apache 2.0）成为开源首选；Judge 侧"通用强模型当裁判"已成为生产实践主流（目的型裁判模型已被通用强模型全面超越）——**裁判按"异构 + 最强判断力"选通用模型**。

### 2.2 对本项目的影响

| 生态位 | 结论 |
|---|---|
| 通用旗舰（V4/K3） | 不做主链（部署过重）；V4-Pro 作 **Judge**（低频 API 形态最合适） |
| Coder 专线 | **生成主选换代**（30B-A3B → 最新代 32B） |
| 专用 SQL 模型 | 单独评估：**不进主链**，列为探索性对照（理由见 §3.4） |
| Embedding | **换代**：BGE-small-zh → Qwen3-Embedding-4B |

## 3. 生成模型选型

### 3.1 候选对照表

| 候选 | 架构 / 许可 | 公开证据 | 顾虑 | 定位 |
|---|---|---|---|---|
| **Qwen3.6-Coder-32B** | 32B 级 · 128K · Apache 2.0 | SQL 专项：**Spider 2.0-Lite 88.7%**（第三方 2026 SQL 评测的裁决之选，首次由全开源模型突破 85% 线）；HumanEval 94.2；同门旧代（Coder-30B）在 DeepEye-SQL 框架下达 BIRD-Dev 73.5% | 2026 上半年代际（非最新旗舰代） | **主选** |
| Qwen3-Coder-Next | 80B / 3B 激活 · 256K · Apache 2.0 | SWE-bench ~73.4–74.2；专为"长程推理 / 复杂工具调用 / 执行失败恢复"设计；**原生非思考模式**（输出无思考块） | 无 SQL 专项证据；Q4 部署需 ≥48GB 显存级（加载门槛高于 32B 单卡） | **对照·效率档** |
| Qwen3.6-35B-A3B | 35B / 3B 激活 · 256K · Apache 2.0 | SWE-bench 73.4 / C-Eval 90.0（新代通用） | 非代码专线 | **对照·通用档**（已可用） |
| Qwen3.6-27B | Dense 27B | SWE-bench 77.2（超越 397B 旗舰） | Dense 推理成本高于同能力 MoE；无 SQL 专项证据 | 备选 |
| Qwen3-Coder-30B-A3B（v0.1 基选） | 30.5B / 3.3B 激活 | DeepEye-SQL 框架 BIRD-Dev 73.5% | 2025-07 代际，已被同门新代超越 | 退役为基线兜底 |
| 专用 SQL 模型（Arctic / Databricks RLVR / SiriusAI / SQLWeaver 等） | 7B–32B · RL 执行反馈 | BIRD 单模型轨 74–76%（超 GPT-5.5 / Claude Opus 4.6） | 中文场景无证据；权重获取性部分不明；与工程层功能重叠 | **不进主链**（见 §3.4） |
| DeepSeek V4-Pro / Kimi K3 | 1T 级 MoE | 通用天花板 | 部署过重（8×H100 级） | 排除主链 |

### 3.2 主选论证（为什么是 Qwen3.6-Coder-32B）

1. **任务同构 + 证据最强**：SQL 是结构化代码；该模型有直接的 SQL 专项证据（Spider 2.0-Lite 88.7%，2026 年全开源最高档），且同门证据链完整（旧代在 DeepEye-SQL 框架 BIRD-Dev 73.5%）。
2. **中文天然支持**（Qwen 系，中文题主体场景的关键）；BIRD 英文题同样在训练分布内。
3. **部署甜点**：Q4 约 24GB——单张 4090 级即可，复现门槛最低；128K 上下文对 2–4K 的需求大幅富余。
4. **输出干净**：代码专线，SQL 输出可解析性优先。

### 3.3 对照设计（数据裁决）

三档同模板对照（黄金集分层 20 条）：**Coder-32B（主选）vs Coder-Next（效率档）vs 35B-A3B（通用档）**——比较执行准确率 / 输出可解析率 / 单请求延迟；绝对差异 ≤2 条视同同水平（取部署与成本更优者）。若效率档同水平，因其 3B 激活的批量成本优势可升为常态主选（重试 / 演示档）。

### 3.4 专用 SQL 模型：评估与排除逻辑

**事实**：该路线的 RL 执行反馈训练让 32B 级模型在 BIRD 单模型轨（英文）超越通用旗舰。**不上主链的三个理由**：

1. **中文场景无证据**——其训练 / 评测基准（BIRD / Spider）以英文为主，本项目题面为中文；
2. **功能重叠**——其核心增量（执行反馈优化）正是本 Pipeline 已内置的能力（守卫执行 + 错误分类 + 定向重试的"外挂回路"）；DeepEye-SQL 已证明"通用 Coder + 工程框架 > 微调系"；
3. **获取与工程确定性**——多数仅有论文 / 榜单曝光（部分仅开源 7B 档），权重可用性、vLLM 兼容性、维护度均不确定。

**处置**：列为"探索性对照"——若后续可稳定获取（如 Arctic-Text2SQL-R1 7B），在附录裁决记录中补一版小样本对照，作为对照记录（"专用 vs 通用 + 工程"的实测比较）；不影响主链。

## 4. Judge 模型选型

### 4.1 异构筛除

生成主选为 Qwen 系 → Judge 候选**排除全部 Qwen 系**。市场扫描后的非 Qwen 候选：

| 候选 | 处置 |
|---|---|
| **DeepSeek V4-Pro**（MIT；1.6T / 49B 激活） | **主选**（API 形态） |
| DeepSeek V4-Flash | 备选（成本更低档） |
| Kimi K3 / GLM-5.3 | 备选（判断力强，但均为大 MoE，部署 / 计价形态待确认） |
| Hunyuan-80B-A13B-Instruct-GPTQ-Int4 | **兜底**（已部署；v0.1 主选降位） |
| Gemma-4 / Phi-4-mini / MiniCPM5-1B | 不纳入（中文与判断力证据不充分） |

### 4.2 主选论证（为什么是 DeepSeek V4-Pro）

1. **异构性**：DeepSeek 源，与 Qwen 系生成模型不同训练谱系——满足硬约束；
2. **判断力天花板**：SWE-bench 80.6 / GPQA-Diamond 90.1 / HLE 48.2（2026 开源第一梯队）——打分任务依赖的通识判断与抗幻觉能力最强档；
3. **中文强**（中国模型）；
4. **成本与形态匹配**：MIT 许可；API 计价约 $0.55 / $0.87 每百万 tokens——Judge 为低频角色（每轮评测 30–50 条解读抽样），单轮成本在分级以内；**1.6T 不适合部署，API 恰是它的正确形态**。

### 4.3 校准与备选链

- 校准：首轮评测抽 30–50 条人工复核，记录"人工-模型一致率"；分歧超阈值 → 备选接管并标注偏置风险。
- 备选链：**V4-Pro（API）→ V4-Flash（API）→ Hunyuan-80B（已部署兜底，配更高人工比例）**。
- 注：裁判专用微调模型（Prometheus 类）已被通用强模型全面超越，不纳入。

## 5. Embedding 选型

| 项 | v0.1 现状（BGE-small-zh） | **v0.2 主选：Qwen3-Embedding-4B** | 对照 / 退路 |
|---|---|---|---|
| 证据 | 轻量、中文向；Linking 抽检 11/11 | Qwen3-Embedding 系：8B 为 MTEB 多语言榜首（70.58），0.6B / 4B / 8B 全档 Apache 2.0；4B 为质量与部署成本甜点 | 0.6B（轻量）/ 8B（极限）；gte-Qwen2-1.5B（已有） |

**为什么 4B（而非 8B / 0.6B）**：本项目检索候选集为百级（9 表 + 52 字段 + 23 条 few-shot），8B 的边际质量提升无法覆盖其部署成本（16GB 级）、4B 已远超现役 BGE-small；0.6B 作为推理资源紧张时的降档方案。**为什么不换更强的 API（Gemini Embedding 2 等）**：检索为每问 2 次的高频调用，本地 / 内网部署的零延迟与离线稳定性优先。

**切换代价（已实测执行）**：重建三层索引（schema ＋ few-shot ＋ doc，均 2560 维）＋ Linking 端到端复检（11/11）——一次性成本分钟级。

## 7. 部署、成本与接入需求（行动清单）

### 7.1 成本口径

**调用量假设（全周期）**：生成 ≈ 5,000 次（开发调试 ＋ 10–20 轮评测 ＋ demo）；Judge ≈ 1,000 次；Embedding ≈ 5,000 次短文本 ＋ 索引重建数次。
**参照单价**：GPU 租赁按公开市场价（24GB 卡约 ¥2/h、48GB 卡约 ¥5/h）；API 按官方公开计价。

### 7.2 部署与成本清单

| 优先级 | 模型 | 用途 | 形态 | 部署要点 | 全周期成本（估） |
|---|---|---|---|---|---|
| **P0** | **Qwen3.6-Coder-32B**（仓库名以 HF / 魔搭官方为准） | 生成主链 + 重试 + 解读 | 部署 | vLLM；Q4 / AWQ 约 24GB，单卡 4090 级；temperature=0 | **¥30–60**（15–30h 挂机） |
| **P1** | **DeepSeek V4-Pro** | 评测 Judge | **API** | OpenAI 兼容端点 + key；低频调用 | **¥10 级**（约 2.3M tokens） |
| **P1** | **Qwen3-Embedding-4B** | Schema Linking + few-shot 检索 | 部署 | sentence-transformers / vLLM 均可；重建双层索引 | ≈ ¥0（常驻小显存） |
| **P2** | **Qwen3-Coder-Next** | 效率档对照（3B 激活） | 部署（可选） | Q4 约 48GB 级显存；原生非思考模式 | ¥50–75（门槛翻倍） |
| 已有 | Qwen3.6-35B-A3B / Hunyuan-80B / Qwen3-Coder-30B-A3B | 对照与兜底 | 已就绪 | 直接复用 | ¥0 |

**全周期合计（估）：¥50–80 量级**；若部署平台为包月 / 额度制，部署项的新增成本趋近于 0。

### 7.3 性价比结论

1. **三个主选恰好都处在最低成本档**：Coder-32B 与 Embedding-4B 为单卡 / 小显存门槛；Judge 的 V4-Pro 在 API 上是角分级花费——**证据最强的组合同时是成本结构最优的组合**，不存在"好用与省钱"之间的取舍。
2. **性价比真正淘汰的是更重的配置**：Coder-Next（48GB 门槛翻倍）降为可选对照；V4 及 1T 级模型一律不做部署。
3. **降级路径（列出但不推荐）**：生成 → 35B-A3B（已有，省 ¥30–60，失去 SQL 专项证据）；Judge → V4-Flash（省约 ¥5）。全周期省钱空间 < ¥100，低于项目产出（可复用文档与实验记录）的价值。
4. **两条免费优化**：① **dev / prod 双档**——开发调试用已就绪的 35B-A3B / Coder-30B-A3B，评测与演示切 Coder-32B（`settings.yaml` 多 provider 配置天然支持）；② 部署形态下"重试与多候选采样"无边际成本（API 形态则为 ×N 花费）。

**模型替代空间**：P0 若部署暂有困难，可先用已就绪的 Coder-30B-A3B 跑通全链，待新模型就绪后经小样本裁决切换（配置 1 行）。

## 附一：角色分配论证（生成 Coder-Next / 裁判 V4-Pro 的对位逻辑）

**这是一道分配题**——两个角色（生成、裁判）× 两条选型线（Qwen Coder 系、非 Qwen 强模型），现行分配为支配解：

| 维度 | 现行分配为何占优 |
|---|---|
| 能力对位 | 生成＝窄分布任务（问题 → SQL 固定转换，可被专精训练强化）→ 代码专线；裁判＝宽分布任务（四元组一致性判断，吃通用底子）→ 通用旗舰最强档 |
| 异构合规 | 生成取 Qwen 系 → 裁判取 DeepSeek 系（不同训练谱系），杜绝自评偏置 |
| 错误杠杆 | 生成错误有执行比对与重试回路兜底（客观显性）；裁判偏差静默污染评测结论 → 裁判可靠性值得溢价 |
| 成本适配 | 生成高频 → 32B 部署（单卡）；裁判低频 → 1T 级 API（按量）——总预算最优分配 |

> 判官不弱于被评者（LLM-as-Judge 通行实践）；判断任务可受益于慢思考，生成侧要求无思考块输出。

## 附三：API 形态的工程处理

**定性**：主链路自部署 ＋ 低频判断角色 API 的混合形态是刻意设计（分配逻辑见附一），不是妥协。API 是否"减分"只取决于一件事——**是否把它当工程面处理**；黑盒式调用才会被追问。

**API 依赖的工程处理（"模型接入层"，接入时实装四件事）**：

| # | 事项 | 现状 | 接入时补 |
|---|---|---|---|
| 1 | 统一接入层 | √ `llm.py`（OpenAI 兼容一次封装，部署 / API 同协议） | provider 配置化（多端点切换＝1 行配置） |
| 2 | 失败处理 | 设计已定（分段批次 / 串行降级 / 逐例落盘） | API 层重试退避 ＋ 限流识别 ＋ 超时 |
| 3 | 备选链 | 设计已定（V4-Pro → V4-Flash → Hunyuan-80B 兜底） | fallback 实装 ＋ 切换日志 |
| 4 | 成本可见 | 成本口径已估（§7） | 成本记账（调用量 × 单价 → 每轮评测报告一行） |

**说明口径（一句话）**："主链路自部署保证成本、延迟与不限量调用；判断角色用 API 换取异构性与最强判断力——API 依赖通过接入层工程化处理（重试 / 限流 / 备选链 / 成本记账），不是黑盒。"

**API 给不了什么、为什么这里不重要**：不能量化 / 微调 / 看 logprobs、最坏延迟不可控——Judge 为低频角色，这些能力在本场景无需求；数据合规上本项目使用公开与自建数据，不涉及数据出境与个人隐私。
