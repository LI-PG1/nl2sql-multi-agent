## 1. 项目定位

**项目背景**（可直接用于 README / demo 文案）：

> 数据分析场景中，取数仍是高门槛环节：业务问题要先翻译成 SQL、跨表关联复杂、指标口径存在同名异义（含税/不含税、退款是否扣减），而真实分析问题往往不是一次取数能回答的。本项目围绕这一场景自建模拟业务数据环境与指标口径体系，实现自主数据分析 Agent：单轮取数走「意图理解 → Schema 定位 → SQL 生成与执行 → 结果解读」全链路（口径歧义主动澄清）；复杂问题由编排层自主分解为多步计划，调用取数、Python 计算、口径文档检索等技能逐步执行并综合成结论。

**实现范围**：模拟数据环境与口径体系自行设计实现；工程链路（编排 / 链接 / 守卫 / 沙箱 / 评测）完整落地，评测数据全部来自本工程实测。

**类型锁定（不变）**：多智能体/图编排；自然语言数据分析全链路；口径歧义处理；SQL 与 Python 双安全控制；自动化评测（内测 + 公开基准外测双轨）。

**技术纵深**：编排 / 后端工程 / 评测 / 迭代闭环——各环节展开到实现细节与实测数据。

**细节可调（当前建议）**：数据底座＝公开数据集 Olist（可换）；图节点拆分＝4 节点（可调）；评测集规模＝150 条左右（可调）；缓存/异步队列＝可选不进一期。

## 2. 系统设计

**两级 Pipeline 总览**（v0.2 新增外层编排层；内层为既有取数链路，整体包装为 `query_data` 技能）：

```
外层·任务编排层（v0.2 新增）：
  起点 plan（任务分解 → 步骤 DAG）
    → 展开 execute_step（按依赖并行/串行；单步失败就近重试 ≤1；异常可追加下钻，max_steps=8 硬限）
    → 收束 respond（正常 / 降级 / 拒答 三路汇入，唯一出口）

内层·技能层：
  query_data ＝ 既有 NL2SQL Pipeline 整体（内部结构不变，见下）
  compute     ＝ Python 计算（沙箱执行：白名单 import / 超时 / 禁网禁文件）
  search_doc  ＝ 口径文档检索（指标口径手册 + 数据字典，Embedding 索引）
```

**内层链路（既有，保留）**：

用户提问 → ① 意图与口径理解（歧义检测 → 澄清或按口径表消解）→ ② Schema 定位（表/字段语义检索 ＋ 同义词映射，压缩候选 schema）→ ③ SQL 生成（few-shot 检索 ＋ 规则约束）→ ④ SQL 校验与执行（只读、白名单、LIMIT）→〔失败〕携带执行反馈重试（环节级重跑）→ ⑤ 结果解读与回答（含口径说明）。

**LangGraph 状态图**：

- 节点：`understand`（理解＋歧义检测）→ `link_schema` → `gen_sql` → `exec_sql` →（条件边：失败 → 回 `gen_sql`，带错误上下文；成功 → `interpret`）→ `respond`；歧义命中时插入 `clarify` 条件分支（追问后回 `understand`）。
- **环节级重跑**：`exec_sql` 失败只回退重跑 `gen_sql / exec_sql`，不重走全图——`understand` 的结论与 `link_schema` 的候选在 state 中保留。
- 状态字段建议：`question / clarified / metric_context / candidate_schema / few_shots / sql / exec_error / rows / retries / answer`。

**关键工程点（施工清单，逐项落进代码）**：

1. **Schema Linking**：表/字段语义索引（BGE Embedding ＋ Milvus Lite/Chroma），问题 → 候选表/字段；同义词映射表（YAML，如"销售额 → payment_value 求和｜price 求和"）；压缩喂给 LLM 的 schema 范围。
2. **few-shot 检索**：按问题与历史 query 的表结构相似度命中示例（自建 30-50 对）。
3. **执行反馈重试**：SQL 报错（字段名/类型/语法）→ 错误信息 ＋ 候选 schema 回传 LLM 重生成；逐轮记录成功率（首轮 vs 重试后）——评测的核心数字之一。
4. **SQL 安全**：只读连接（SQLite 只读模式 / MySQL 只读账号）；白名单校验（仅 SELECT；禁 PRAGMA / DROP 等；强制 LIMIT）；可用 sqlglot 做语法级校验。
5. **口径层**：`config/metrics.yaml`（指标名、定义、口径变体、计算逻辑、适用表）；同名异义 → 澄清追问或默认口径并注明。
6. **缓存（可选二期）**：问题 → SQL 缓存；口径版本变更触发失效。
7. **评测脚本**：`eval/run_eval.py` 一键跑黄金集出报告。
8. **迭代闭环（评测驱动）**：跑分层黄金集 → 失败归因（Schema 选错 / SQL 生成错 / 口径错 / 该澄清未澄清 / 应拒答未拒答）→ 定向优化（同义词表 / few-shot / 规则约束 / 口径表）→ 回归对比；迭代资产全部配置化，前后指标可证。
9. **任务编排层（v0.2 新增）**：Planner（任务分解为 2–6 步 DAG）／Executor（按依赖拓扑并行 + 串行，单步失败就近重试 ≤1 次，异常可追加下钻步骤，max_steps=8 硬限）／Verifier（空结果 / 数量级异常等规则校验）／Synthesizer（多步 observation 综合成结论，数字必须来自 observation）。
10. **Python 沙箱（v0.2 新增）**：受限 `exec`（白名单 import、单次 ≤10s 超时、禁网络禁文件、上游数据只读注入）＋ 执行异常回填 LLM 重生成 ≤1 次 → 仍败该步降级——与 SQL 守卫并列构成"两类代码执行、两套安全策略"。
11. **口径文档源（v0.2 新增）**：`config/metrics.yaml` 渲染为口径手册与数据字典（一指标一节切片），入 Embedding 索引，支撑"先查口径再算数"的异构推理链路。

**模型与组件**：见 `模型选型.md`（v0.2 市场级选型）——生成主选 Qwen3.6-Coder-32B（部署）、Judge 选 DeepSeek V4-Pro（API）、Embedding 选 Qwen3-Embedding-4B（部署）；**Planner 角色开思考模式（规划受益于慢思考）、Executor / Synthesizer 关思考（执行要干净输出）**。数据库 ＝ SQLite。

## 5. 评测设计

- **主指标**：SQL 执行准确率（标准 SQL 与生成 SQL 的结果集规范化比对）；**分层报告**（五类分别统计）。
- **过程指标**：重试增益（首轮 → +1 次 → +2 次成功率曲线）；澄清命中率（歧义题是否触发追问）；平均端到端时延。
- **人工抽检**：端到端回答正确率（抽 30-50 条人工判）。
- **迭代对比**：优化前后分层数字同集对比（失败归因 → 定向优化 → 回归）。
- **产出**：`eval/report.md` ＝ 分层数字表 ＋ 失败案例 5-10 例 ＋ 失败归因。

**v0.2 多步任务评测（新增）**：

| 指标 | 口径 |
|---|---|
| 最终答案正确率 | 数值容差比对（相对误差 ≤1% 或整数精确） |
| 步骤序列准确率 | 实际技能调用序列 vs 期望序列（含参数要点） |
| 任务完成率 | max_steps 内走到 respond 且未降级 |
| 编排增益 | 同多步任务集：无规划基线（直接单轮问答）vs 有编排的失败率对比 |

**v0.2 双轨外测（新增）**：内测轨＝自建多步黄金集（上表指标）；外测轨＝KDD DataSpace 官方公测包（60 题全量，双链路 A/B，**官方评测器**判分——vendored），产出 `eval/report_kdd.md`（标注：官方公测包、模型档位、本地自测口径）。

## 9. 设计问答（常见追问与对应实现）

- NL2SQL 怎么做才"稳"？（Schema 压缩、few-shot、执行反馈重试——带首轮/重试后数字）
- 口径歧义怎么处理？（口径表 ＋ 澄清追问）
- 生成的 SQL 怎么保证安全？（只读 ＋ 白名单 ＋ 强制 LIMIT）
- LangGraph 为什么合适？（状态图、条件路由、环节级重跑 vs 线性链）
- 评测怎么做的？（分层黄金集、结果集比对、失败归因；多步任务：步骤序列比对）
- 效果怎么迭代提升？（评测驱动：失败归因 → 定向优化 → 回归对比——带前后数字）
- **多步分析问题怎么拆**（v0.2）？（Planner 分解 DAG → 按依赖并行执行 → 综合；带编排增益对照数字）
- **让模型写 Python 怎么防风险**（v0.2）？（沙箱四件套：白名单 import / 超时 / 禁网禁文件 / 只读数据注入）
- **和公开 benchmark 怎么对标**（v0.2）？（KDD 公测集 + 官方评测器口径）
