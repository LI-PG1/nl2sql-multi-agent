### 0.2 端到端 Pipeline（项目核心）

**本项目的重心＝端到端 Pipeline**——供给层（数据与资产）与保障层（评测与迭代）均服务于它；§1-§6 是其构件，§7-§8 是它的质量保障。

**结构＝起点 →（展开）→ 收束**：单一入口进入 → 主干上按需展开两条回路 → 全部路径收束到唯一出口。

```
【供给】Olist → orders.db → Schema 索引 ｜ 配置资产（口径 / 同义词 / few-shot / 提示词）

【起点】单一入口：question ＋ mode（interactive / eval）→ 状态初始化
   ↓
【展开】主干单向推进；异常以回路就近回退（已完成阶段的结果保留）
   主干：① 理解 → ③ 链接 → ④ few-shot → ⑤ 生成 → ⑥ 守卫执行 → ⑦ 解读
   回路 A｜澄清：① ─〔歧义〕→ ② 澄清 →（消解后）回①（≤1 轮；超限用默认口径继续主干）
   回路 B｜重试：⑥ ─〔失败〕→ 错误分类 → 携带反馈回⑤（≤2 次）
   ↓
【收束】唯一出口 respond——全部路径汇入，无游离终态
   正常路径：⑦ 解读 → respond（回答 ＋ 溯源：SQL / 口径说明 / 澄清记录）
   降级路径：重试耗尽 → respond（已完成步骤 ＋ 已尝试 SQL 与错误）
   拒答路径：① 识别变更类请求 → respond（拒答说明；守卫拦截为兜底）
   统一动作：输出 ＋ 落运行记录（trace）→ 终

【保障】黄金集评测 → 失败归因 → 定向优化（配置 / 提示词 / few-shot）→ 回归对比
```

**核心链阶段**：

| 阶段 | 职责 | 输入 → 输出 | 分支 / 兜底 | 章节 |
|---|---|---|---|---|
| ① 理解 | 指标识别、口径匹配、歧义检测（含变更类意图识别） | 问题 → metric_hits / ambiguity | 歧义 → ②；变更类请求 → 拒答收束 | §4.2 / §1.1 |
| ② 澄清 | 口径消解（interactive）/ 记录（eval） | 歧义组 → clarified | ≤1 轮，超限用默认口径 | §6 |
| ③ 链接 | 候选表 / 字段压缩 | 问题 → candidate_schema | 召回优先，宁多勿漏 | §2 |
| ④ few-shot | 示例检索 | 问题 ＋ 候选表 → few_shots | 无交集退 top-1 | §3 |
| ⑤ 生成 | SQL 生成（口径 ＋ 示例约束） | 全上文 → sql | 重试携带错误反馈 | §4.2 / §4.3 |
| ⑥ 守卫执行 | 安全校验 ＋ 只读执行 | sql → rows | 失败分类重试 ≤2 → 降级输出 | §5 / §4.3 |
| ⑦ 解读 | 结果解读 ＋ 口径说明 | rows → answer | 空结果规则兜底 | §4.2 |

**构建策略——先通后深**：先用最小实现（规则 / Mock）把整条链打通并保持可跑，再逐段替换为真实实现、按深挖要点加深——**任何时候都有一条可演示的完整 Pipeline**（施工清单见 §11）。

**M2 施工顺序（Pipeline 优先，先通后深）**

```
最小配置层 + Schema 索引构建
  → Pipeline 全节点骨架（节点先用规则 / Mock 实现）→ 端到端干跑通
  → 逐段替换为真实实现：Schema Linking → few-shot → 口径 / 澄清
  → 真实 LLM 跑通 → 运行产物与 CLI → 文档同步
```

## 1. 配置层（`config/`）

原则：**一切可迭代资产配置化**——口径、同义词、表字段说明、提示词均为独立文件；迭代闭环（§8）通过修改这些文件 + 回归评测达成，代码不动。

### 1.1 `metrics.yaml` — 口径层

设计 3 组歧义（黄金集"口径歧义 / 需澄清"两类的出题依据）：

```yaml
version: 0.1
ambiguity_groups:
  - id: amount_scope            # 组①：金额范围
    triggers: ["销售额", "营收", "GMV", "交易额", "营业额"]
    variants:
      - id: payment_total
        name: 支付总额
        definition: order_payments.payment_value 合计（默认）
        sql_hint: SUM(payment_value)
        default: true
      - id: goods_only
        name: 商品金额
        definition: order_items.price 合计（不含运费）
        sql_hint: SUM(price)
      - id: delivered_only
        name: 仅已送达订单
        definition: payment_value 合计且 orders.order_status = 'delivered'
        sql_hint: SUM(payment_value) + 状态过滤
    clarify_question: "销售额有几种口径：① 支付总额（默认）② 商品金额 ③ 仅已送达订单——按哪一种统计？"
  - id: cancel_handling         # 组②：取消订单是否扣减
    triggers: ["净销售额", "实际成交", "有效订单"]
    clarify_question: "是否剔除已取消 / 不可用订单？① 剔除（默认净口径）② 全部计入"
  - id: time_field              # 组③：时间口径
    triggers: ["月度", "趋势", "按月"]
    clarify_question: "按哪个时间统计：① 下单时间（默认）② 支付时间 ③ 送达时间"
metrics:
  - id: gmv
    name: 销售额
    ambiguity_group: amount_scope
  - id: order_count
    name: 订单量
    definition: COUNT(DISTINCT orders.order_id)
  - id: avg_order_value
    name: 客单价
    definition: 销售额 ÷ 订单量（口径随金额口径联动）
```

## 2. Schema Linking（`src/embed.py` + `src/index_store.py` + `src/linking.py` + `scripts/build_index.py`）

**目标**：把"全表全字段"压缩为与问题相关的候选 schema——降低生成难度（NL2SQL 准确率的第一杠杆）。

### 2.1 Schema 块构建（`scripts/build_index.py`）

- 数据源：`sqlite_master` + `PRAGMA table_info` + 外键 + `config/schema_notes.yaml`（合并人工说明）；枚举字段（如 order_status）采样低基数 distinct 值（≤10 个）写入说明。
- 产出两级文本块：

```jsonl
// data/index/schema_blocks.jsonl（示意）
{"id": "table:order_payments", "type": "table", "tables": ["order_payments"], "text": "表 order_payments（订单支付表，一个订单可有多条支付记录）：order_id（外键→orders），payment_type（支付方式），payment_value（支付金额，销售额默认口径字段）……"}
{"id": "field:order_payments.payment_value", "type": "field", "tables": ["order_payments"], "text": "order_payments.payment_value：支付金额；销售额默认口径；与 order_items.price（商品金额）、freight_value（运费）区分"}
```

### 2.2 向量化与索引

- `src/embed.py`：`Embedder` 接口——`embed(texts: list[str]) -> np.ndarray`（已 L2 归一化）。
  - `BgeEmbedder`：sentence-transformers，默认 `BAAI/bge-small-zh-v1.5`（可换 bge-m3）；
  - `MockEmbedder`：确定性字符 n-gram 哈希 → 256 维——**仅用于干跑 / 单测验证链路机制，不代表真实检索质量**。
- `src/index_store.py`：`VectorIndex`——`build(rows, embedder)` / `search(q_vec, k)` / `save(dir)` / `load(dir)`；持久化 = `data/index/<name>.npz`（向量）+ `<name>.jsonl`（元数据，顺序对齐）；余弦相似（点积）。
- 默认轻量实现（numpy），接口预留 Chroma / Milvus 替换位（数据规模百级，环境兼容性优先）；替换只在存储层，Linking 逻辑不变。
- 构建命令：`python scripts/build_index.py --name schema --backend mock|bge`。

### 2.3 检索与候选压缩（`src/linking.py`）

```
输入：question（含澄清补充后的完整表达）
步骤：① 向量检索 table 块 → 取 top-N（3）
      ② 收集候选表的 field 块 → 按相似度排序取 top-M（20）
      ③ 同义词命中加权：问题和 synonyms.yaml 匹配的词 → 对应字段加权 +0.1
输出：candidate_schema = { tables, fields, synonym_hits, schema_text }
      schema_text = 压缩后的 schema 文本（喂给 gen_sql 的"可用表字段"部分）
```

### 2.4 验收标准

对 10-15 条人工问题（覆盖单表 / 多表 / 口径类）抽查：**涉及表全部进入候选**（召回优先，宁多勿漏）；top_tables 可调至 4。Mock 后端可跑通全流程（机制验收）；真实质量用 BGE 后端 + 上述抽查（质量验收）。

## 3. few-shot 检索（`config/fewshots.jsonl` + `src/fewshots.py`）

### 3.1 数据格式

```jsonl
{"id": "fs-001", "question": "2018 年各州的销售额排名前五？", "sql": "SELECT c.customer_state, ROUND(SUM(p.payment_value),2) AS gmv FROM order_payments p JOIN orders o ON o.order_id = p.order_id JOIN customers c ON c.customer_id = o.customer_id WHERE o.order_purchase_timestamp >= '2018-01-01' GROUP BY 1 ORDER BY gmv DESC LIMIT 5", "tables": ["orders", "order_payments", "customers"], "tags": ["join", "ranking", "time_filter"], "note": "州=客户所在州；销售额默认支付口径"}
```

- 规模目标 20-30 条（M2 首版），覆盖三类：单表聚合 / 多表 join / 口径限定（显式写"不含运费"等消解词）。
- 初始化：`scripts/gen_fewshots.py`（骨架模板 + 人工撰写；不自动生成 SQL，保证正确性）。

### 3.2 检索策略

1. 向量检索问题文本 → 取 top-5；
2. **表结构过滤**：few-shot.tables 与 candidate_schema.tables 有交集者优先（相似度为主、交集为过滤器）；
3. 取 top-2~3 组装进 gen_sql 提示；无交集时回退 top-1（避免空手）。

### 3.3 防泄漏纪律

few-shot 与黄金集**不得重复**：构建时脚本校验（问题文本去重 + SQL 归一化比对），重复即报警。确保评测数字不被"背题"污染。

## 4. LangGraph 全链路升级（`src/graph.py` 核心）

### 4.1 状态（State）字段

```python
question / mode(interactive|eval) / clarified / clarify_count
metric_hits / ambiguity                      # 理解层
candidate_schema / few_shots                 # 检索层
sql / error / error_type / retries           # 生成与执行
columns / rows / answer                      # 输出
guards / timings / done                      # 观测（时延打点、守卫轨迹）
```

### 4.2 节点契约

| 节点 | 输入 | 行为 | 输出 |
|---|---|---|---|
| `understand` | question（+clarified） | 指标提及识别 → 匹配 metrics.yaml；歧义组触发检测（触发词命中且问题未自行消解） | metric_hits / ambiguity |
| `clarify` | ambiguity | 条件节点：interactive=向用户提问等待回答（`ask` 回调）；eval=采用默认口径并标记 `clarify_fired` | clarified / clarify_count |
| `link_schema` | question(+clarified) | §2.3 流程 | candidate_schema |
| `gen_sql` | 全上文 | 组装提示：候选 schema + 口径 context + few-shot + 问题（+错误反馈） | sql |
| `exec_sql` | sql | guard → 只读执行 | rows/columns 或 error/error_type |
| `interpret` | rows + 口径 | 生成解读（含口径说明）；规则兜底（空结果 / 纯数值直接格式化） | answer |
| `respond` | 全上文 | 组装最终输出：answer + sql + 口径说明 + 澄清记录 | done |

### 4.3 条件边与错误协议

```
understand → (ambiguity 且未澄清 且未超轮数) → clarify → understand
           → （变更类请求）→ respond（拒答收束，不经检索与生成）
           → link_schema → gen_sql → exec_sql
exec_sql  → done    : interpret → respond → END
          → retry   : gen_sql（携带 error / error_type / 上次 SQL，环节级重跑——保留理解与链接结果）
          → give_up : respond（重试耗尽：输出降级说明 + 已尝试的 SQL 与错误）
```

**展开与收束约定**：主干单向推进（理解 → 链接 → 生成 → 执行 → 解读）；异常以回路**就近回退**（澄清回 `understand`、重试回 `gen_sql`，已完成阶段的结果保留在 state）；**变更类请求在理解层直接收束**（拒答说明，不经检索与生成；守卫拦截为兜底）；**全部路径收束于 `respond` 唯一出口 → END**（正常解读后进入 / 重试耗尽进入降级输出 / 拒答直接进入），无游离终态。

**错误分类（error_type）与定向反馈**：

| 分类 | 来源 | 重试提示要点 |
|---|---|---|
| `guard:multi_statement` / `guard:forbidden` | guard 字符串 | 仅输出单条 SELECT |
| `exec:no_such_table` / `exec:no_such_column` | sqlite 异常 | 附候选 schema，要求只从中选表/字段 |
| `exec:syntax` | sqlite 异常 | 附错误位置提示，要求重写 |
| `exec:other` | 兜底 | 通用重试 |

### 4.4 双模式

- **interactive**：澄清真实提问（CLI `input` / 后续 Gradio 按钮）；最多 1 轮。
- **eval**：非交互批量——澄清"触发即记录 + 按默认口径继续执行"；供 §7 "澄清命中率 / 误触发率"统计。

### 4.5 时延打点

节点级计时（`timed` 包装器）写入 `timings`；报告输出端到端 P50/P95 与分段占比（定位瓶颈：检索 vs 生成 vs 执行）。

### 4.6 运行产物（编排产出）

每次运行落一份结构化记录 `runs/<时间戳>_<id>.json`：

```json
{"question": "...", "mode": "interactive",
 "nodes": [{"name": "understand", "ms": 812, "out": {"metric_hits": ["gmv"], "ambiguity": "amount_scope"}}],
 "clarify": {"fired": true, "question": "...", "answer": "支付总额"},
 "retries": [{"n": 1, "error_type": "exec:no_such_column", "sql": "..."}],
 "final": {"sql": "...", "rows_n": 5, "answer": "..."}}
```

- 用途：调试 / 评测归因 / 演示回放（讲解"这里为什么重试"时直接翻记录）；
- **图结构导出**：Mermaid 源码（由 graph 对象生成），作为 README 架构图来源；
- **两条剧本路径定型**：① 澄清路径（歧义问题 → 追问 → 消解后生成）；② 重试路径（首轮失败 → 错误反馈 → 修正成功）——各保存一份样本记录，作为演示素材；
- 批量评测时逐例落盘（供失败案例回放），默认不入库、样本可选收录。

## 5. SQL 守卫与执行（保持 + 接入）

- `guard.py` 接口不变（`validate_sql -> (ok, cleaned_or_err)`）；错误字符串 → error_type 映射表（§4.3）在 graph 侧维护。
- `run_sql` 已具备只读连接 + fetchmany 上限（200 行保护），保持。
- `pipeline.py`（M1 直连）**保留**为"直连基线对照"（评测章节用于对照"引入编排与链接后的提升"），不再扩展功能。

## 6. 澄清追问设计

- **触发条件（保守，防扰民）**：① 歧义组触发词命中，且问题未包含消解词（"不含运费""仅已送达""剔除取消"等——消解词表维护在 `metrics.yaml` 的变体关键词）；② 同一轮不重复追问。
- **提问形态**：模板优先（metrics.yaml `clarify_question` + 选项）；模型生成仅作兜底润色。
- **轮数**：interactive ≤1；eval 0（记录触发）。
- **指标**：澄清命中率（该问的问了）+ 误触发率（不该问的没问）——双向考核，防止"过度澄清"。

## 7. 评测系统（`eval/`）

### 7.1 黄金集（`eval/golden_set.jsonl`）

```jsonl
{"id": "g-001", "question": "2018 年各州的销售额排名前五？", "category": "join", "expected_tables": ["orders","order_payments","customers"], "expected_sql": "……", "expect_clarify": false, "expect_refuse": false, "note": "默认支付口径"}
{"id": "g-042", "question": "销售额是多少？", "category": "ambiguous", "expect_clarify": true, "note": "触发 amount_scope 澄清；默认口径计分"}
{"id": "g-088", "question": "把取消的订单从库里删掉", "category": "refuse", "expect_refuse": true, "note": "应被守卫拦截并给出说明"}
```

- **五类分布**：`basic`（单表聚合）/ `join`（多表）/ `ambiguous`（触发澄清）/ `refuse`（应拒答）/ `filter`（时间与条件筛选）。
- **构建流程**：LLM 起草 → **人工逐条校验**（问题合理 + 参考 SQL 可执行）→ 参考 SQL 执行生成标准答案（运行时计算，缓存于 `eval/answers/`）。
- 规模：目标 150 条；首版 ≥60 条且五类覆盖均衡，后续凭 badcase 扩增。**与 few-shot 零重叠（§3.3）**。

### 7.2 打分口径

- **执行准确率（主指标）**：结果集规范化比对——数值 `round(x,2)`、字符串去空白小写、列对齐优先按列名（退化按位置）、行序无关（multiset）；列数一致。
- **拒答类**：判定"拒答 + 明确说明"为通过（主路径为理解层直接拒绝、不经检索与生成；守卫拦截为兜底）。
- **澄清类**：`clarify_fired` 命中为通过；默认口径下的执行结果另行统计（不计入主指标）。
- **过程指标**：重试增益（首轮成功 vs 重试后成功曲线）；端到端时延 P50/P95；误触发率。
- **端到端正确率**：解读类回答用 **LLM-as-Judge（异构 judge 模型，避免自评偏置）** 评分；抽 30-50 条人工复核校准。

### 7.3 报告（`eval/report_vN.md`）

指标总表（含与上版对比列）+ 五类分层表 + 失败类型分布 + 失败案例 5-10 例（含归因）。

### 7.4 失败归因分类（taxonomy，供 §8 迭代映射）

`schema_miss`（候选缺表/字段）/ `sql_gen`（生成错）/ `metric_wrong`（口径错）/ `clarify_miss`（该问未问）/ `false_clarify`（不该问却问）/ `refuse_miss`（应拦未拦）/ `exec_other`。

## 8. 迭代闭环（评测驱动）

**流程**：① 跑评测 → ② 逐条失败归因（taxonomy）→ ③ 按映射表定向改进 → ④ 同集回归 → ⑤ `eval/CHANGELOG.md` 记录前后指标。

**改进映射表**：

| 失败类型 | 改进动作（全部为配置/资产修改，代码不动） |
|---|---|
| `schema_miss` | 补 `schema_notes.yaml` / 调 `synonyms.yaml` / 调 top-k |
| `sql_gen` | 加 few-shot 例 / 改 `prompts/gen_sql.md` / 增规则约束 |
| `metric_wrong` | 补 `metrics.yaml` 口径与变体 / 调澄清触发词 |
| `clarify_miss` | 补触发词 / 调 `clarify_question` 文案 |
| `false_clarify` | 补消解词表 |
| `refuse_miss` | 补 guard 规则（联动 guard.py） |

**CHANGELOG 记录格式**：

```
## v0.2（2026-10-XX）
- 变更：metrics.yaml 新增 xxx；prompts/gen_sql.md 调整 yyy（关联文件列出）
- 指标：执行准确率 62% → 71%（同集 60 条）；澄清命中 4/6 → 6/6
- 备注：xxx
```

**版本纪律**：`config/*.yaml` 与 `prompts/*` 文件头带 `version`；每次迭代 bump 并在 CHANGELOG 对照。验收要求 **≥1 轮完整迭代记录**（前后数字可证）。
