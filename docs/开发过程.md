## 2. 关键节点与实测数据

### 2.1 首轮评测暴露的都是口径问题

黄金集首跑 61/72，失败集中在 basic 与 join 两类。逐条看下来，错误不在 SQL 语法，而在口径：
品类名用葡语还是英文、商品用 `product_id` 还是名称、客户数是否去重（同一 `customer_id` 有多个订单）、
配送时长取哪两个时间戳之差、「订单平均金额」是行级 AVG 还是先聚合到订单级再平均、时间过滤按哪个字段。
这些问题无法靠改代码解决，只能把口径固化进配置。

v0.1 把七条默认口径写进 `prompts/gen_sql.md` 并细化 `metrics.yaml` / `synonyms.yaml` / `schema_notes.yaml`，
升至 69/72；v0.2 强化时间规则（统一按下单时间、年份用 `LIKE` 匹配）与均值语义后到 72/72。
这条经验确立了迭代纪律：**只改配置资产，代码不动**——每轮改动的影响才能被干净地归因。

### 2.2 重试的边界

环节级重跑只回 `gen_sql`，保留已完成的链接结果。这个设计在大部分执行错误上有效（写错列名、函数不存在），
但有一类错误修不了：候选表缺失（`no_such_table` 且目标表不在候选集）。此时重生成再多次也没用，
必须先重检索。当前保留了这个升级位但未启用，等真实错误分布足够再按数据决定。

### 2.3 多步编排的迭代链

30 条多步集上，最终答案正确数经五轮迭代：14 → 23 → 25 → 28 → 29。每轮的提升都对应可定位的失败：

| 轮次 | 主要问题 | 处理 |
|---|---|---|
| 1→2 | 计划不自包含、字段名被改写、聚合粒度错 | 计划提示词 v0.4：要求自包含、字段原文采用、明确聚合纪律；compute 增加代码提取兜底；判分口径对齐设计 |
| 2→3 | 上游结果未正确注入下游 | 步骤间数据传递改为显式引用（取数结果作文本参考、计算结果注入 `data` 变量） |
| 3→4 | 题面字段与归时口径未注明 | 计划要求注明来源字段与时间归属；补全环境口径 |
| 4→5 | 评价类任务的过滤条件被重复加 | 归因为模型行为项（ms-24），保留展示而非硬改 |

期间还修了一处基建缺陷：并行步骤在同一秒写 trace 导致文件名冲突（PermissionError），改为文件名唯一后缀。

### 2.4 外测的三次判断

第一次跑 BIRD Mini-Dev 得 54.6%（272/498）。这个数字低于黄金集，但两者不可比——黄金集是受控口径，
外测是全库 schema 注入且关闭专属口径层。为确认不是实现退化，又跑了 CSpider（68.7%）与 Archer（23.5%）：
三者的差异反映任务难度（中文语义解析 / 多跳反事实推理）而非实现质量，Archer 的低分说明单次生成一条 SQL
在复杂推理上存在结构上限。

DataSpace 公测轨的两条链路（A 单发 / B 取数+解读）跑了两版。v1 为 A 18.3% / B 16.7%，
v2 加入提示词纪律与重试工程后升到 23.3% / 20.0%，双链路零退化。这条轨的判分用官方评测器，
判分逻辑与本工程其余基准不同源，因此单列不与其它分数横向比较。

### 2.5 嵌入后端对照

索引层同探针下，自部署 Qwen3-Embedding-4B 得 21/23，BGE-small 得 19/23。差距不大但方向一致，
决定接线 4B 并回归全套评测（黄金集 72/72 无退化）。代价是单查询时延从 6ms 升到 345ms（公网服务），
在高频调用下可接受——这条权衡记录在 `eval/CHANGELOG.md`。

## 3. 工程纪律

- **配置即资产**：口径、同义词、few-shot、提示词全部外置，迭代只改 `config/`；
- **可解释优先**：每次运行落 trace（节点轨迹、时延、SQL、行数），评测归因与问题复现都基于它；
- **安全前置**：SQL 守卫与 Python 沙箱都在执行前生效，不依赖模型自律；
- **对照实验单一变量**：所有「有 X vs 无 X」的比较都保证同任务、同模型，只切一个开关。
